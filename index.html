从零设计 Tiled GEMM：Layout、Layout Algebra、CuTe 编译、TMA / Pipeline / Warp Specialization / PDL 练习

20 道一小时左右的练习，沿着一条主线走完：先只从硬件需求出发，亲手推导一个 64×64 Tiled GEMM 需要的五种映射（CTA tile、Copy TV、SMEM swizzle、MMA fragment、accumulator），再把它们拼成一个完整可验证的 GEMM；然后用 Layout Algebra 重新表达这些映射、看 CuTe 在编译期怎样化简和检查它们；最后把 TMA、mbarrier pipeline、warp specialization 和 PDL 加进来，得到一个结构完整的现代 GEMM，并用代价模型选配置。期望答案来自本机编译运行的真实 CuTe，也给出真实的 CUTLASS 源码对照。

怎么用这套练习

建议顺序与依赖

  • A1 → A2 → A3 → A4 → A5：五个空间映射，最后串成一个可验证的 64×64 GEMM。这是全套的主线。
  • B1、B2：用代数重写 A1–A3、推导向量宽度（需要 A 组的结论）。
  • C1、C2：编译期化简与合法性检查（可以在 B 之后或之前做）。
  • D1 → D2 → D3 → D4：TMA、mbarrier 流水线、warp specialization、PDL。
  • E1 → E2：完整的 Hopper 风格 GEMM（用到 A、D 的全部部件），最后在约束下搜索配置。

需要什么硬件

Track A–E 的测试只用 CPU（Python + numpy），几秒跑完。oracle/ 和 playground/ 里的 C++ 程序只在主机上编译真实的 CuTe / CUTLASS 头文件，也不需要 GPU。TMA、mbarrier、setmaxnreg、PDL 这些机制必须在 Hopper（SM90）或更新的 GPU 上才能真正运行；讲解页里凡是“在 GPU 上验证”的说法都标明了没有在本机核对。

领域知识

总览：一条主线、三类抽象、六个 track
这套练习的主线：先只从硬件需求出发设计一个 Tiled GEMM，看我们怎样“自然地发明”各种 layout；再看这些 layout 怎样用代数组合、CuTe 在编译期怎样化简和检查它们；最后把 TMA、pipeline、warp specialization 和 PDL 加进来，得到一个结构完整的现代 GEMM。
硬件心智模型：汽车工厂类比 + RTX 5090 的真实数字
先把 GPU 想成一座汽车工厂：订单（Grid）拆给生产小组（CTA），小组进车间（SM），车间里有4 条产线（SMSP），每条产线一次派一个 32 人班组（Warp）干活。然后给每一层配上 RTX 5090（GB202 · sm_120）的真实数字，并对照本套练习默认的 Hopper（H100 · sm_90）。目标是解题时脑子里有画面，手上有量级。
执行模型：thread、warp、SMSP、CTA 怎样跑起来
写 CUDA 代码时，你写的是“一个线程”的程序；硬件执行时，按 32 个线程一组的 warp 发射指令；warp 固定在 SM 的某个 SMSP 上，CTA 固定在某个 SM 上。这一页把这几层粒度一次讲清楚：SIMT 和 SIMD 的区别、lane 什么时候不满、哪些指令必须整个 warp 一起执行、为什么不能让单个线程调用 mma 、一个 SM 能同时发射和驻留多少 warp 与 CTA，以及每条指令去 TensorCore、FP32/INT32 lane 还是别的单元，它们怎样在同一个 SMSP 上同时工作。
怎样定 CTA / tile / warp 的数量：以 RTX 5090 为例
一个 GEMM 里有一堆“数量”：CTA tile 多大、有几个 tile、grid 开几个 CTA、每个 CTA 几个warp、几级 stage。它们不是同一层的东西：有的是硅片焊死的，有的是指令规定的，有的是你选的，剩下的都是推出来的。这一页以 RTX 5090 为例，把这些参数分层，给出从头定一个配置的顺序和每一步的算式，并用 8192³ BF16 GEMM 完整算一遍。
BM、BN、BK 各管什么：SMEM、GMEM、L2 的约束落在哪一维
CTA tile 有三个维度：BM、BN 决定这个 CTA 负责的输出块有多大，BK 决定每一轮沿 K 搬多厚的一片输入。这一页用三张图讲清楚：三个维度在矩阵上分别在哪里；为什么显存 cache line、L2和 SMEM bank 的 128 B 粒度只会碰到 BK；以及寄存器、L2 复用、SM 利用率、SMEM 容量、同步开销这些约束各自落在哪个维度上。最后用两组扫描表（固定 BM×BN 改 BK，固定 BK 改BM×BN）把影响量化，并解释在本套例子里为什么 BK 最先被定下来。
配置决策：一步一步定下一个 GEMM 配置（含 split-K / Stream-K）
这一章把“怎样定一个 GEMM 配置”拆成 9 步（第 0–8 步），每一步给出要回答的问题、算式、5090 上的数字和常见的坑。重点讲第 4 步“要不要切 K”：split-K 和 Stream-K 是什么、三种归约方式、怎样选 S、什么时候切 K 反而更慢。全章用 6 个形状贯穿：大方阵、中等方阵、tile 少而 K长、小 GEMM、LLM decode 的瘦长矩阵、K 很短。所有估算都来自playground/sizing_5090.py ，可以换成自己的形状重跑。
端到端例子：A[1024×1024] · B[1024×256] 在 RTX 5090 上怎样定配置、怎样运行
用一个具体问题把前面所有东西串起来：A 是 1024×1024，B 是 1024×256，在 RTX 5090 上算 C= A·B（BF16 输入、FP32 累加、BF16 输出）。从“这个问题有多大”开始，比较 7 种 tile / warp /split-K 方案各自卡在哪里，选定一个方案后把五个映射（CTA tile、Copy TV、SMEM swizzle、MMA fragment、累加器）逐个写出具体坐标，最后按时间顺序走一遍 kernel 怎样运行。映射里的坐标都是用真实 CuTe 在主机上打印出来的。
从零设计一个 Tiled GEMM：为什么我们会自然地发明这些 Layout
先暂时忘掉 CuTe 的 API。假设我们自己要写一个尽可能快、又不容易出错的 GEMM kernel，只从 GPU 硬件和数据流出发，逐步推导需要哪些映射；最后再回头看，CuTe 为什么会有这些 layout 和代数操作。这一页对应 Track A。
Layout Algebra 与编译：映射怎样组合，编译器怎样化简
Track A 手写的五张映射表，用 Layout Algebra 可以写成几行组合；这些组合在编译期被化简、检查，最后由 CUDA 工具链生成机器码。这一页讲清楚三层各自做什么、“零成本抽象”到底是什么意思，对应 Track B 和 C。
时间维度：TMA、Pipeline、Warp Specialization、PDL
Layout 解决“数据在哪里、由谁持有”；执行机制还要解决“何时搬、何时算、谁先运行、谁必须等待”。这一页讲 TMA、异步流水线、warp specialization 和 PDL 怎样加入一个 GEMM，以及它们和 Layout Algebra 的耦合程度，对应 Track D。
真实代码导读：从 sgemm_sm80 到 SM90 warp-specialized GEMM
把“设计结构伪代码”换成真实的 CUTLASS 代码：先读 SM80 的 sgemm_sm80.cu（cp.async + ldmatrix + mma.sync + 多级 SMEM 流水线），再读 SM90 的 warp-specialized cooperative kernel（TMA + mbarrier + WGMMA + setmaxnreg + PDL）。每一段都标出它对应五个映射中的哪一个、哪个练习。
