总览：一条主线、三类抽象、六个 track 硬件心智模型：汽车工厂类比 + RTX 5090 的真实数字 执行模型：thread、warp、SMSP、CTA 怎样跑起来 怎样定 CTA / tile / warp 的数量：以 RTX 5090 为例 BM、BN、BK 各管什么：SMEM、GMEM、L2 的约束落在哪一维 配置决策：一步一步定下一个 GEMM 配置（含 split-K / Stream-K） 端到端例子：A[1024×1024] · B[1024×256] 在 RTX 5090 上怎样定配置、怎样运行 从零设计一个 Tiled GEMM：为什么我们会自然地发明这些 Layout Layout Algebra 与编译：映射怎样组合，编译器怎样化简 时间维度：TMA、Pipeline、Warp Specialization、PDL 真实代码导读：从 sgemm_sm80 到 SM90 warp-specialized GEMM 参考资料与边界说明
Track A · 从零设计：五个空间映射问题
A1CTA 切分：C tile、K 循环、local_tile 视图与边界谓词 A2线程怎样搬数据：从 ThrLayout / ValLayout 推出 Copy TV 映射，数 sector 与向量宽度 A3Shared memory 怎样摆：行主序、Swizzle<2,2,2> 与 bank conflict 的实测 A4MMA fragment：从 PTX 的 groupID 规则推出 m16n8k16 的 TV_A / TV_B / TV_C，再扩展到 2×2 warp 并在寄存器里累加 A5把五个映射拼成完整的 Tiled GEMM：逐 CTA、逐 K 片模拟，统计 sector、wavefront 与 mma，并追踪 C[5][7]
Track B · 用 Layout Algebra 重新表达
B1用 Layout Algebra 重写 Track A：local_tile = zipped_divide + 切片，Copy TV = right_inverse(raked_product)，SMEM = Swizzle ∘ Layout B2一次能搬多宽：max_common_vector 推出向量宽度，swizzle 把它压到 2^M，padding 和对齐让它失效，再选 copy atom
Track C · CuTe 编译期在做什么
C1编译期化简：把 copy 地址写成表达式，做常量折叠、强度削减、coalesce 与循环外提，再和真实编译器的汇编对照 C2编译期合法性检查：复刻 CuTe 的 static_assert，并给一个 GEMM 配置做完整体检
Track D · 时间维度：TMA、Pipeline、Warp Specialization、PDL
D1TMA box：描述符合法性、expect_tx、越界填零与 swizzle 后的 SMEM 位置 D2mbarrier 多级流水线：phase 奇偶、PipelineState、producer / consumer 协议与三种同步 bug D3Warp specialization：setmaxnreg 寄存器预算与 Cooperative / Ping-pong 调度 D4PDL：两个串联 GEMM 的提前启动、等待位置与正确性检查
Track E · 完整成熟的 Tiled GEMM
E1完整成熟的 Tiled GEMM：TMA → swizzled SMEM 环形缓冲 → mbarrier 流水线 → warp specialization → epilogue → PDL E2选配置：CTA tile、stage 数、cooperative / pingpong 与 swizzle，在硬件约束下用代价模型排序
Track F · 上机：用真实 CuTe 在 GPU 上写高效 Tiled GEMM（RTX 5090）
F1第一个真实 CuTe kernel：local_tile + local_partition + SMEM，用 CUDA core（FFMA）算 GEMM F2第一个 Tensor Core GEMM：TiledCopy（cp.async 16 B）+ swizzle 过的 SMEM + TiledMMA（mma.sync） F3多级 cp.async 流水线 + ldmatrix + 寄存器双缓冲：写出 sgemm_sm80 的完整主循环 F4边界与 epilogue：M、N 不整除时的谓词加载，α·acc + β·C，FP32 → BF16 写回 F5在 5090 上扫配置：tile、stage、warp 排列、split-K，用代价模型预测并和 cuBLAS 对比

边界说明

  • CUTLASS / CuTe API 会随版本和 GPU 架构变化；具体的 atom、TMA 操作、MMA 指令、pipeline API 和 launch 参数，以目标版本的官方文档和示例为准。
  • Track A–E 的测试不需要 GPU。 Layout 相关的答案来自真实 CuTe 的主机端程序；D2 的 PipelineState 来自真实 CUTLASS 头文件；TMA、mbarrier、warp specialization 和 PDL 的运行时行为是照着 CUTLASS 源码写的协议与时间线模拟器，数字是模型数字，不是实测。
  • Track F 在真实 GPU 上运行。 参考解在 RTX 5090（sm_120，CUDA 13.0）上编译、对拍、计时过；主机部分的期望答案同样来自真实 CuTe（oracle/f1|f2|f4_*.cpp）。讲解页里的 TFLOPS 是量级参考，具体数字取决于驱动、时钟和 CUDA 版本。
  • 这些机制真正跑起来需要 Hopper（SM90）或更新的 GPU。讲解页里“在 GPU 上可以这样验证”的说法没有在本机核对。
