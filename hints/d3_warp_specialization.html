D3 · Warp specialization：setmaxnreg 寄存器预算与 Cooperative / Ping-pong 调度

有了 TMA 和 mbarrier 流水线，发搬运指令的线程几乎不干活，却和做 MMA 的线程占着一样多的寄存器。Hopper 的 CUTLASS GEMM 把一个 CTA 拆成 1 个 producer warp group 和 2 个 consumer warp group，用 setmaxnreg 把寄存器从前者挪给后者；两个 consumer 再按 Cooperative 或 Ping-pong 两种方式分工。本题算清这笔寄存器账（为什么恰好是 40 和 232），并模拟两种调度的时间线，找出 Ping-pong 什么时候赢、什么时候反而输。

题面速览

  • 背景知识：先读 时间维度 的 warp specialization 一节；D2 的流水线是这里 producer 和 consumer 之间的通道。
  • 在体系里的位置：两份 kernel 是 cooperative 和 pingpong。寄存器常数在 pingpong 的 LoadRegisterRequirement，重分配指令在 reg_reconfig.h，Ping-pong 的有序屏障是 OrderedSequenceBarrier。
  • 你要实现：launch_regs_per_thread、validate_setmaxnreg、register_plan、accumulator_regs、schedule_cooperative、schedule_pingpong、steady_per_tile。常数和 Segment、Schedule 已经给出。
  • 关键规则：
    1. 启动时每线程寄存器 = floor(65536 / threads / 8) × 8；384 线程是 168。
    2. setmaxnreg 的目标值是 8 的倍数、在 [24, 256]；dec 只能降、inc 只能升；重分配后的总数不能超过启动时的总数。
    3. Cooperative：两个 WG 一起算一个 tile，每 tile M + E/2。
    4. Ping-pong：tile j 归 WG 1 + j%2；MMA 链和 epilogue 链各自严格交替；每 tile max(M, E)。

验收要点：启动寄存器按 8 取整 · setmaxnreg 的两条规则 · CUTLASS 默认的 40 / 232 恰好用满 64512 · 重负载的 24 / 240 也恰好用满 · 两种混用超出 2048 · 方向错误和对齐错误 · 3 个 consumer WG 时最多只能升到 160 · 累加器寄存器（64、128）· Ping-pong 4 个 tile 与 Cooperative 2 个 tile 的逐段时间线 · 三组参数下 8 个 tile 的 makespan · Tensor Core 利用率 · Ping-pong 的交替与不自重叠 · 稳态公式与模拟一致 · E 超过 2M 时 Cooperative 反超 · 空调度。

第一次出现的术语
  • WG（warp group）：4 个连续 warp = 128 线程。WGMMA（warp-group 级矩阵乘指令）以 WG 为单位发射。
  • warp specialization：同一个 CTA 里不同 WG 执行不同的代码路径（producer 只发 TMA，consumer 只做 MMA 和 epilogue），用 mbarrier 通信。
  • setmaxnreg（setmaxnreg.inc/dec.sync.aligned.u32 N）：Hopper 的 PTX 指令，整个 WG 一起把每线程寄存器上限改成 N。dec 释放的寄存器回到 CTA 的池子，inc 从池子里取。
  • epilogue：MMA 算完之后把累加器转换、加 bias、写回 C 的那一段。Hopper 上通常经 SMEM 再用 TMA store。
  • persistent kernel：CTA 数等于 SM 数，每个 CTA 循环处理多个输出 tile。两个 consumer 交替处理 tile 就建立在这上面。

直觉与类比

类比 · 一间厨房三个人

一间厨房只有一台大灶（Tensor Core），三个人分工：一个跑腿买菜（producer：发 TMA），两个掌勺（consumer）。跑腿只需要一个小篮子，所以把他的大推车（寄存器）让给两个掌勺的放配料——这就是 setmaxnreg：总推车数不变，40 + 232 + 232 正好等于开门时每人 168 的总和。两个掌勺怎么用一台灶？Cooperative 是两人一起炒同一锅大菜，炒完再一起装盘，装盘时灶空着；Ping-pong 是两人各炒一锅，A 装盘的时候 B 正在灶上炒，灶几乎不停。但装盘台（epilogue 的 SMEM 和 TMA store）也只有一个，两人轮流用：如果装盘比炒菜还慢，瓶颈就变成装盘台。

逐步演示

▶ M = 10，E = 4 的 Ping-pong，4 个 tile
1. t = 0–10：WG1 算 tile 0

OrderedSequenceBarrier 的 group 0 从相反的 phase 起步，所以 WG1 的第一次 wait 立即通过；WG2 的 wait 要等 WG1 arrive。段：(1, mma, 0, 0, 10)。

2. t = 10–20：WG2 算 tile 1，WG1 写回 tile 0

WG1 在 10 时 arrive（把 MMA 位交给 WG2），然后做 epilogue (1, epi, 0, 10, 14)；同时 WG2 (2, mma, 1, 10, 20)。Tensor Core 没有停。

3. t = 20–30：WG1 回来算 tile 2

tile 2 的 MMA 要同时等“tile 1 的 MMA 结束”（20）和“WG1 自己写完 tile 0”（14）：max(20, 14) = 20。WG2 在 20–24 写回 tile 1。

4. 稳态

4 个 tile 的 makespan 44，Tensor Core 忙 40。8 个 tile 时 Ping-pong 84、Cooperative 96（每 tile 10 + 4/2 = 12），利用率 0.952 对 0.833。E = 10 时是 90 对 120；E = 16 时 epilogue 链成为瓶颈，每 tile 16，仍略胜 Cooperative 的 18（138 对 144）。

易错点

  • 以为 setmaxnreg 能凭空多出寄存器。 inc 只能拿走 dec 放回池子的部分。40 / 240 混用需要 18432 个却只放出 16384 个：E_BUDGET: final 66560 registers > launch allocation 64512。测试 test_register_plan_errors。
  • 启动寄存器不按 8 取整。 65536 / 384 = 170.67，实际只有 168；按 170 算账就对不上。测试 test_launch_regs_round_down_to_8。
  • inc 的目标低于启动值。 测试 test_register_plan_errors 里 160 < 168 报 E_ALLOC_BELOW_LAUNCH。
  • 以为 Cooperative 两个 WG 一起算就快一倍。 Tensor Core 是 SM 共享的；两个 WG 一起算只是把一个 tile 分成两半，MMA 时间不变。真正省下的是 epilogue 各写一半（E/2）。测试 test_cooperative_timeline。
  • 把 Ping-pong 的稳态写成 (M + E) / 2。 那只是单个 WG 的约束。epilogue 也被有序屏障串起来，所以还要不小于 E：稳态是 max(M, E)。测试 test_cooperative_wins_when_epilogue_is_long。
  • 只让 MMA 交替、忘了同一个 WG 要先写完上一个 tile。 tile j 的 MMA 必须等 epi_end[j−2]：累加器寄存器还被上一个 tile 占着。测试 test_pingpong_invariants_on_random_inputs 检查一个 WG 的各段互不重叠。

对照文档

“例如一个 warp group 负责 TMA load（producer），其他 warp group 负责 MMA（consumer）。这种分工可以减少搬运和计算之间的资源竞争，并让异步执行更清晰。这里增加的不只是新的 Layout：还需要角色分配、pipeline 状态、barrier、warp-group 同步以及架构特定的指令语义。”

文档说的“资源竞争”，最具体的一项就是寄存器：本题把它量化成 64512 这笔账。“warp-group 同步”在 Ping-pong 里是 MMA 和 epilogue 两条有序链；“架构特定的指令语义”是 setmaxnreg 的 8 对齐、[24, 256] 范围和 inc / dec 的方向。

真实代码

寄存器常数（简化自 pingpong kernel，Cooperative 的常数相同）：

static_assert(NumMMAThreads == 128, "Pingpong kernel must have TiledMMA operating using 128 threads.");
static_assert(MaxThreadsPerBlock == 384, "Pingpong kernel must have 384 threads in total.");
static constexpr int RegsPerThread = (TileM * TileN * sizeof(ElementAccumulator)) / (NumMMAThreads * sizeof(uint32_t));
static constexpr bool HeavyRegisterPressure = RegsPerThread >= 208;
static constexpr uint32_t LoadRegisterRequirement = !HeavyRegisterPressure ? 40 : 24;
static constexpr uint32_t MmaRegisterRequirement = !HeavyRegisterPressure ? 232 : 240;

RegsPerThread 就是本题的 accumulator_regs。角色分派和两条有序链（简化自 pingpong 的 operator()）：

if (warp_group_role == WarpGroupRole::Producer) {
  cutlass::arch::warpgroup_reg_dealloc<LoadRegisterRequirement>();    // setmaxnreg.dec 40
  ...                                                                 // TMA 发射、调度器、epilogue load
} else {                                                              // Consumer0 / Consumer1
  cutlass::arch::warpgroup_reg_alloc<MmaRegisterRequirement>();       // setmaxnreg.inc 232
  while (work_tile_info.is_valid()) {
    math_wg_order_barrier.wait();  collective_mainloop.mma(...);      math_wg_order_barrier.arrive();
    math_wg_order_barrier.wait();  collective_epilogue.store(...);    math_wg_order_barrier.arrive();
    ...                                                               // 跳到下一个属于自己的 tile（隔一个）
  }
}

有序屏障的关键：group 0 从相反的 phase 起步（“Group 0 starts with an opposite phase”），arrive() 通知 (group_id + 1) % Length 后 ++stage_。SequenceDepth = 2 的两个 stage 正好是“MMA”和“epilogue”，所以两条链各自交替。

关键问题

  1. 40 和 232 是怎么来的？如果改成 3 个 consumer WG（512 线程），consumer 最多能升到多少？
  2. 同样 128×128 的 tile，Cooperative 和 Ping-pong 每个 consumer 线程各要多少累加器寄存器？这对 tile 大小的选择意味着什么？
  3. 在什么条件下 Ping-pong 比 Cooperative 快？什么时候反过来？
L2思路拆解与常见坑拆解与常见坑（中度剧透）
  • register_plan：算出 threads、launch、两个总数，然后按顺序检查：两个目标值各自合法 → load_regs ≤ launch → mma_regs ≥ launch → final ≤ launch_total。
  • schedule_cooperative：一个时间游标 t；每个 tile 给 WG1、WG2 各记一段 [t, t+M] 的 mma，再各记一段 [t+M, t+M+E/2] 的 epi。
  • schedule_pingpong：两个字典 mma_end、epi_end；按递推式逐个 tile 算，不存在的项按 0。
  • 最后统一排序（开始时间，再 wg），makespan 取最大结束时刻，tensor_core_busy = n·M。
  • steady_per_tile：写出公式，再用 (makespan(n+2) − makespan(n)) / 2 自己验证一遍。
L3关键问题的答案几乎是答案（重度剧透）
答案
  1. 384 线程启动时每线程 168，总 64512。producer 降到 40 放出 128 × 128 = 16384 个；两个 consumer 各升 64，正好要 2 × 128 × 64 = 16384。512 线程时启动 128，producer 降到 24 放出 13312 个，3 个 consumer 平分每线程最多再加 34.67，按 8 对齐只能到 160。
  2. Cooperative 两个 WG 分一个 tile，每线程 128·128/256 = 64；Ping-pong 一个 WG 拿整个 tile，每线程 128。所以 Ping-pong 的 tile 通常要小一半（例如 64×128），或者接受更高的寄存器压力（≥ 208 时 CUTLASS 改用 24 / 240）。
  3. Ping-pong 每 tile max(M, E)，Cooperative 每 tile M + E/2。max(M, E) ≤ M + E/2 当且仅当 E ≤ 2M：epilogue 不超过 MMA 的两倍时 Ping-pong 不慢，E ≤ M 时 epilogue 被完全藏住。E > 2M（很小的 K、很重的 epilogue fusion）时 Cooperative 更快。E = 0 时两者相同。

"""D3 · Warp specialization：寄存器重分配预算、Cooperative 与 Ping-pong 两种调度的时间线— reference solution.

Hopper 的 CUTLASS GEMM（include/cutlass/gemm/kernel/sm90_gemm_tma_warpspecialized_{cooperative,pingpong}.hpp）
一个 CTA 有 3 个 warp group（WG，128 线程 = 4 个 warp）：
- WG0 = Producer：只发 TMA、跑调度器，几乎不需要寄存器，启动后立刻 `setmaxnreg.dec` 降到 40个；
- WG1、WG2 = Consumer0 / Consumer1：做 WGMMA（warp-group 级矩阵乘）和 epilogue，`setmaxnreg.inc` 升到 232 个，
  用来放累加器。两份 kernel 的常数完全相同：LoadRegisterRequirement = 40、MmaRegisterRequirement = 232
  （每线程寄存器 >= 208 的“重负载”配置用 24 / 240）。
区别在两个 Consumer 怎么分工：
- Cooperative：两个 WG 一起算同一个输出 tile（TiledMMA 用 256 线程），一起做 epilogue（各写一半）。
- Ping-pong：两个 WG 轮流各算一个完整 tile；一个有序屏障（OrderedSequenceBarrier<2,2>）让两个 WG 的
  MMA 严格交替、epilogue 也严格交替，于是一个 Consumer 写回 tile j 的时候，另一个正在用 Tensor Core 算 tile j+1。

寄存器模型
- 一个 SM 有 REGS_PER_SM = 65536 个 32 位寄存器。启动时每线程寄存器数
  launch_regs_per_thread(threads) = floor(65536 / threads / 8) * 8（寄存器以 8 个为单位分配）；384 线程 → 168。
- setmaxnreg 的目标值必须是 8 的倍数，且在 [24, 256] 内（validate_setmaxnreg，错误码 E_NREG_MULT8 / E_NREG_RANGE）。
- register_plan(load_wgs, load_regs, mma_wgs, mma_regs)：threads = 128 * (load_wgs+ mma_wgs)；
  launch_total = launch_regs * threads；final_total = 128*(load_wgs*load_regs + mma_wgs*mma_regs)；
  freed = 128*load_wgs*(launch_regs − load_regs)；needed = 128*mma_wgs*(mma_regs −launch_regs)；
  ok 当且仅当两个目标值都合法、load_regs <= launch_regs <= mma_regs，且 final_total <= launch_total。
  返回 dict：threads, launch_regs, launch_total, final_total, freed, needed, ok, errors（列表，错误码开头：
  E_NREG_MULT8、E_NREG_RANGE、E_DEALLOC_ABOVE_LAUNCH、E_ALLOC_BELOW_LAUNCH、E_BUDGET）。
- accumulator_regs(tile_m, tile_n, threads)：fp32 累加器每元素一个寄存器，均分给参与的线程：tile_m*tile_n/threads。

时间模型（单位任意；一个持久化 CTA 依次处理 n_tiles 个输出 tile；生产者的 TMA 假设总能跟上）
- mainloop：算完一个 tile 的全部 MMA 需要的 Tensor Core 时间（Tensor Core 是 SM 内共享的，两个 WG 一起算也不会更快）。
- epilogue：一个 WG 写回一整个 tile 的时间（Cooperative 两个 WG 各写一半，用 epilogue/2）。
- schedule_cooperative：tile j 的 MMA 在 tile j−1 的 epilogue 结束后开始；MMA 段 [s, s+M]，随后 epilogue 段 E/2，
  两个 WG 同时出现在同一段里（segments 里各记一条）。
- schedule_pingpong：tile j 归 WG j%2。mma_start_j = max(mma_end_{j−1}, epi_end_{j−2})；
  epi_start_j = max(mma_end_j, epi_end_{j−1})；epi_end_j = epi_start_j + E（不存在的项按 0 算）。
- Schedule：segments（Segment(wg, kind, tile, start, end)，kind 为 "mma" 或 "epi"，按开始时间、再按 wg 排序）、
  makespan（最后一段的结束时刻）、tensor_core_busy = n_tiles*M、utilization = tensor_core_busy / makespan。
- steady_per_tile(kind, M, E)：稳态下每个 tile 的平均间隔。cooperative → M + E/2；
  pingpong → max(M, E)：MMA 链每 tile 要 M，epilogue 链每 tile 要 E，单个 WG 每两个 tile 要 M + E（不会更紧）。
  所以 E <= 2M 时 Ping-pong 不慢于 Cooperative，E > 2M 时 Cooperative 反而更快。

API
    REGS_PER_SM, THREADS_PER_WG, SETMAXNREG_MIN, SETMAXNREG_MAX, Segment, Schedule given
    launch_regs_per_thread(threads) -> int
    validate_setmaxnreg(count) -> list[str]
    register_plan(load_wgs=1, load_regs=40, mma_wgs=2, mma_regs=232) -> dict
    accumulator_regs(tile_m, tile_n, threads) -> int
    schedule_cooperative(n_tiles, mainloop, epilogue) -> Schedule
    schedule_pingpong(n_tiles, mainloop, epilogue) -> Schedule
    steady_per_tile(kind, mainloop, epilogue) -> float
"""

from dataclasses import dataclass, field

REGS_PER_SM = 65536
THREADS_PER_WG = 128
SETMAXNREG_MIN = 24
SETMAXNREG_MAX = 256


@dataclass(frozen=True)
class Segment:
    wg: int
    kind: str          # "mma" | "epi"
    tile: int
    start: float
    end: float


@dataclass
class Schedule:
    segments: list = field(default_factory=list)
    makespan: float = 0.0
    tensor_core_busy: float = 0.0
    utilization: float = 0.0


def launch_regs_per_thread(threads: int) -> int:
    # 硬件按 8 个寄存器一组分配；编译器给 __launch_bounds__(384, 1) 的 kernel 最多分到 168个。
    return (REGS_PER_SM // threads) // 8 * 8


def validate_setmaxnreg(count: int) -> list[str]:
    errs = []
    if count % 8:
        errs.append(f"E_NREG_MULT8: setmaxnreg {count} is not a multiple of 8")
    if not (SETMAXNREG_MIN <= count <= SETMAXNREG_MAX):
        errs.append(f"E_NREG_RANGE: setmaxnreg {count} not in [{SETMAXNREG_MIN}, {SETMAXNREG_MAX}]")
    return errs


def register_plan(load_wgs: int = 1, load_regs: int = 40, mma_wgs: int = 2, mma_regs: int = 232) -> dict:
    threads = THREADS_PER_WG * (load_wgs + mma_wgs)
    launch = launch_regs_per_thread(threads)
    launch_total = launch * threads
    final_total = THREADS_PER_WG * (load_wgs * load_regs + mma_wgs * mma_regs)
    freed = THREADS_PER_WG * load_wgs * (launch - load_regs)
    needed = THREADS_PER_WG * mma_wgs * (mma_regs - launch)
    errors = validate_setmaxnreg(load_regs) + validate_setmaxnreg(mma_regs)
    # dec 只能往下降，inc 只能往上升：方向反了 setmaxnreg 本身就是非法的。
    if load_regs > launch:
        errors.append(f"E_DEALLOC_ABOVE_LAUNCH: producer target {load_regs} > launch {launch}")
    if mma_regs < launch:
        errors.append(f"E_ALLOC_BELOW_LAUNCH: consumer target {mma_regs} < launch {launch}")
    # inc 拿到的寄存器来自 dec 释放进 CTA 池子的那部分：总量不能超过启动时分到的。
    if final_total > launch_total:
        errors.append(f"E_BUDGET: final {final_total} registers > launch allocation {launch_total}")
    return dict(threads=threads, launch_regs=launch, launch_total=launch_total, final_total=final_total,
                freed=freed, needed=needed, ok=not errors, errors=errors)


def accumulator_regs(tile_m: int, tile_n: int, threads: int) -> int:
    return tile_m * tile_n // threads


def _finish(segs: list, n_tiles: int, mainloop: float) -> Schedule:
    segs.sort(key=lambda s: (s.start, s.wg))
    makespan = max((s.end for s in segs), default=0.0)
    busy = n_tiles * mainloop
    return Schedule(segments=segs, makespan=makespan, tensor_core_busy=busy,
                    utilization=(busy / makespan) if makespan else 0.0)


def schedule_cooperative(n_tiles: int, mainloop: float, epilogue: float) -> Schedule:
    segs, t = [], 0.0
    for j in range(n_tiles):
        # 两个 WG 一起：MMA 段里 Tensor Core 忙，epilogue 段里 Tensor Core 闲着（这是 Cooperative 的代价）。
        for wg in (1, 2):
            segs.append(Segment(wg, "mma", j, t, t + mainloop))
        t += mainloop
        for wg in (1, 2):
            segs.append(Segment(wg, "epi", j, t, t + epilogue / 2))
        t += epilogue / 2
    return _finish(segs, n_tiles, mainloop)


def schedule_pingpong(n_tiles: int, mainloop: float, epilogue: float) -> Schedule:
    segs = []
    mma_end, epi_end = {}, {}
    for j in range(n_tiles):
        wg = 1 + j % 2
        # 有序屏障：MMA 必须排在上一个 tile 的 MMA 之后（Tensor Core 轮流用）；
        # 同一个 WG 还得先写完自己上一个 tile（j−2）。
        s = max(mma_end.get(j - 1, 0.0), epi_end.get(j - 2, 0.0))
        mma_end[j] = s + mainloop
        segs.append(Segment(wg, "mma", j, s, mma_end[j]))
        # epilogue 也严格交替：等自己的 MMA 完、也等上一个 tile 的 epilogue 完。
        e = max(mma_end[j], epi_end.get(j - 1, 0.0))
        epi_end[j] = e + epilogue
        segs.append(Segment(wg, "epi", j, e, epi_end[j]))
    return _finish(segs, n_tiles, mainloop)


def steady_per_tile(kind: str, mainloop: float, epilogue: float) -> float:
    if kind == "cooperative":
        return mainloop + epilogue / 2
    if kind == "pingpong":
        # 两条独立的有序链：MMA 链（Tensor Core）和 epilogue 链。每个 WG 自己的 (M + E) /2 永远不超过 max(M, E)。
        return max(mainloop, epilogue)
    raise ValueError(f"unknown schedule kind {kind!r}")
