领域知识

时间维度：TMA、Pipeline、Warp Specialization、PDL

Layout 解决“数据在哪里、由谁持有”；执行机制还要解决“何时搬、何时算、谁先运行、谁必须等待”。这一页讲 TMA、异步流水线、warp specialization 和 PDL 怎样加入一个 GEMM，以及它们和 Layout Algebra 的耦合程度，对应 Track D。

TMA：把大块搬运交给专用硬件

传统的线程协作 copy 要每个线程生成地址、发 load / store。TMA 让一个指定线程发起描述符驱动的多维搬运，由硬件完成整块 tensor 的传输（D1，0z_tma_tensors.md）。三样东西各管一件事：

东西 管什么
layout tensor 的形状、stride、SMEM 排布和 swizzle
Copy Atom / TMA 描述符 用什么机制搬、搬哪个 tile（box），见 make_tma_copy_desc
barrier / pipeline 数据什么时候到、消费者什么时候能读

TMA 没有让 layout 失去意义：它改变的是“谁执行搬运”，不是“数据的坐标和物理排布”。

异步流水线：让搬运和计算重叠

顺序执行是 load 0 → compute 0 → load 1 → compute 1，搬运延迟完全暴露。多 stage 流水线用多个 SMEM buffer：计算当前 stage 时，producer 预取后面的 stage；consumer 确认数据 ready 后再读；用完后释放，producer 才能复用（D2，pipeline.md）。

▶ 一个 stage 的生命周期（CUTLASS PipelineTmaAsync）
1. 拿到空 buffer

producer 在 empty[s] 上按当前 phase 等待，确认这个 stage 已经被 consumer 释放；然后 leader 线程在 full[s] 上 arrive_and_expect_tx(transaction_bytes)：告诉屏障“还会有这么多字节到达”（producer_acquire）。

2. 发出 TMA

copy(tma_load_a.with(*tma_barrier, mcast_mask_a), tAgA(...), tAsA(...))：TMA 搬完会自动在 full[s] 上扣掉对应字节数（collective load）。

3. 屏障完成

到达数和字节数都清零时，mbarrier 的 phase 位翻转。等待方看的就是这个 phase。

4. consumer 等数据

consumer 在 full[s] 上按自己的 phase 等待（consumer_wait）。phase 记错就会死锁，或者读到上一轮的数据：D2 的测试专门构造这些错误。

5. 计算并释放

warpgroup_arrive(); cute::gemm(...); warpgroup_commit_batch(); warpgroup_wait<K_PIPE_MMAS>(); 之后 consumer_release 在 empty[s] 上 arrive，这个 buffer 回到 producer 手里（collective mma）。stage 下标和 phase 由 PipelineState 维护：下标转一圈，phase 翻一次。

Warp specialization：不同 warp 承担不同角色

一个 warp group 负责 TMA（producer），其他 warp group 负责 MMA（consumer）。producer 几乎不需要寄存器，consumer 需要大量寄存器放累加器，所以 Hopper 上还会用 setmaxnreg 重新分配：CUTLASS cooperative kernel 里 producer 降到 40 个、consumer 升到 232 个（LoadRegisterRequirement / MmaRegisterRequirement）。D3 让你在 64K 寄存器的预算下检查这些数，并比较两种调度：

调度 做法 好处
Cooperative 两个 consumer warp group 合作算同一个输出 tile tile 更大，单个 tile 更快
Ping-pong 两个 consumer warp group 交替处理不同 tile 一个做 epilogue 时另一个在做 mainloop，epilogue 被隐藏

PDL：跨 kernel 的提前启动

PDL 不是 kernel 内的流水线，它解决的是两个有依赖关系的 kernel 之间的启动时机（D4，dependent_kernel_launch.md）：

角色 做什么 在 CUTLASS 里
producer kernel 到达合适位置时发出“可以启动后继”的信号（cudaTriggerProgrammaticLaunchCompletion / griddepcontrol.launch_dependents） launch_dependent_grids
consumer kernel 提前开始做与 producer 输出无关的工作；读依赖数据之前等待（cudaGridDependencySynchronize / griddepcontrol.wait） wait_on_dependent_grids
host 用 extensible launch API 设置 programmatic stream serialization；CUDA Graph 用 programmatic dependency edge dependent_kernel_launch.md
注意 · PDL 的正确性边界

trigger 不表示 producer 的写入已经可见；wait 等的是 producer 完成并把内存刷出去。consumer 在 wait 之前只能访问明确与 producer 无关的数据。PDL 不是取消依赖，也不是让两个有数据竞争的 kernel 自动安全并行。

真实的 cooperative kernel 里，producer warp 在第一次读 GMEM 之前调用 wait_on_dependent_grids()，consumer 在处理最后一个 tile 时调用 launch_dependent_grids()（wait 的位置 · trigger 的位置）。

PDL 的真正收益只在系统层面才看得见：单个 GEMM 测不出来，要在 CUDA Graph 或 stream 里有一串依赖的 kernel、每个 kernel 的 launch 与 prologue 开销相对它的运行时间不可忽略时（小 batch 推理、decode 阶段的一串小 GEMM），把下一个 kernel 的启动、setup 和独立 operand 的预取藏到上一个 kernel 的尾巴里。CUTLASS 的 example 63 README 也提醒：大部分收益要在端到端应用里看，overlap_ratio 和 prefetch_ratio 要按端到端时间 autotune。D4 的 best_trigger 就是这个 autotune 的最小模型。

四种机制和 Layout Algebra 的耦合程度

机制 作用范围 回答的问题 和 Layout Algebra 的关系
Layout Algebra 编译期 / 数据映射 坐标、线程、value、地址怎样对应 核心对象
TMA + SMEM layout kernel 内搬运 一个 tile 怎样描述并搬到指定排布 紧密耦合
Async pipeline / barrier kernel 内时序 哪个 stage 何时 ready、何时可复用 中等耦合
Warp specialization kernel 内分工 哪些 warp 生产、哪些消费 中等耦合
PDL kernel 之间 后继 kernel 何时启动、在哪里等待 弱耦合

Layout 是空间关系，pipeline 是 kernel 内的时间关系，PDL 是 kernel 之间的时间 / 依赖关系。 设计时先用 Layout Algebra 解决数据映射，再用 TMA、pipeline、barrier 解决 kernel 内的重叠，最后看 kernel 之间有没有可以提前做的独立工作。

类比 · 餐厅的三种协调

Layout 是“哪道菜放在哪个盘子、由哪个服务员端”；pipeline 是厨房里“上一道还在炒，下一道已经在切菜，但切好的菜要等锅空了才能下”；warp specialization 是“专门有人切菜、专门有人炒”；PDL 是“下一桌客人还没吃完上一道，厨房已经开始准备他们点的、和上一道无关的凉菜，但热菜要等上一道的锅腾出来”。
